## Guía de git del equipo

**Ramas**

| Rama | Uso |
|---|---|
| `main` | Versión entregable. Solo recibe fusiones desde `develop` cuando se cierra una entrega (en este repositorio de evidencias, `main` es la rama de trabajo). |
| `develop` | Integración: siempre compila y pasa las pruebas. Nadie hace commits directos aquí. |
| `feature/<tema>` | Función nueva (`feature/admin-inspection`). |
| `fix/<tema>` | Corrección (`fix/logout-session-expired`). |
| `docs/<tema>` | Solo documentación (`docs/update-october-17`). |
| `chore/<tema>`, `refactor/<tema>`, `test/<tema>` | Mantenimiento, reorganización de código o pruebas. |

**Commits** con el formato de [Conventional Commits](https://www.conventionalcommits.org/es/v1.0.0/), en inglés y en presente: `tipo(alcance): qué cambia`.

- Tipos: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`.
- Ejemplos: `feat(admin): add the vehicle inspection report screen like the web` · `fix(auth): ignore a late 401 after logout` · `docs(manuals): document the inspection report in the mobile app`.
- Un commit por cambio lógico: no mezclar una corrección con una función nueva ni con documentación.

**Flujo de trabajo**

```bash
git checkout develop && git pull --ff-only          # 1. partir de develop actualizado
git checkout -b fix/<tema>                           # 2. rama propia
# ... cambios, pruebas y commits pequeños ...
git checkout develop && git pull --ff-only          # 3. traer lo del equipo
git merge --no-ff fix/<tema>                         # 4. fusionar conservando la rama en el historial
git push origin develop fix/<tema>                   # 5. subir develop y la rama
```

- Antes de fusionar: compilar, correr las pruebas y, si cambia la interfaz, revisar el diseño adaptable a 360 y 768 px.
- Nunca subir archivos `.env`, contraseñas, tokens ni datos personales reales; solo `.env.example`.
- Las versiones de entrega se marcan con tags semánticos (`v1.0.0`) al pasar `develop` a `main`. El 23 de octubre de 2026 se creó `v1.0.0` en 8 repositorios y el 24 en payment-service (PR #2 fusionado). El 26 de octubre de 2026 salió `v1.1.0` en los 10 repositorios, con los arreglos del 23 y del 24 de octubre (la app móvil tuvo así su primera versión), y ese mismo día `v1.1.1` en la web, la app móvil, payment-service e infra.
- Despliegue: el servidor de Azure corre `main` (`v1.1.0` y `v1.1.1`) desde el 26 de octubre de 2026. El despliegue continuo está activo desde esa noche: cada fusión aprobada a `main` cambia producción sola (respaldo, `:prev`, espera a que todo quede sano y comprobación de la web y la API; `rollback.sh` vuelve a `:prev` y nunca se baja de versión), y la app móvil recibe la actualización por internet si la huella nativa coincide con la del APK publicado (Documento de Despliegue, secciones 1.3.12 y 4.3.4).

## Team Git Guide

- **Branches:** `main` (deliverable version), `develop` (integration, always builds and passes the tests), and short-lived `feature/<topic>`, `fix/<topic>`, `docs/<topic>`, `chore/<topic>`, `refactor/<topic>`, and `test/<topic>` branches. In this evidence repository the working branch is `main`.
- **Commits:** [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/), in English and present tense (`type(scope): what changes`), one commit per logical change.
- **Flow:** branch from an updated `develop`, commit, pull `develop` again, merge with `git merge --no-ff`, and push `develop` and the branch. Build, run the tests, and check the responsive design at 360 and 768 px before merging interface changes.
- **Security:** never commit `.env` files, passwords, tokens, or real personal data; only `.env.example`.
- **Releases:** semantic tags (`v1.0.0`) when `develop` is moved to `main`. On October 23, 2026 `v1.0.0` was created in 8 repositories and on the 24th in payment-service (PR #2 merged). On October 26, 2026 `v1.1.0` shipped in the 10 repositories with the fixes of October 23 and 24 (the mobile app got its first version), and that same day `v1.1.1` in the web, the mobile app, payment-service, and infra.
- **Deployment:** the Azure server runs `main` (`v1.1.0` and `v1.1.1`) since October 26, 2026. Continuous deployment is active since that night: every approved merge into `main` changes production on its own (backup, `:prev`, waiting for everything to be healthy, and checking the web and the API; `rollback.sh` goes back to `:prev` and it never downgrades), and the mobile app gets the over-the-air update if the native fingerprint matches the published APK's (Deployment Document, sections 1.3.12 and 4.3.4).
